# P1 - Dynamic Academic Performance and Risk Analysis Engine

## What the program does

The program stores student records and enables the user to work with them from a menu:

```
------------------------- MENU -------------------------
 1. Add a new student record
 2. Display all student records
 3. Sort students (by grade / name / ID)
 4. Calculate the average grade
 5. Find the top performing student
 6. Search for a student (by ID / name)
 7. Remove a student record
 8. Custom analysis - Academic Risk Index
 9. Display the summary report
10. Exit
--------------------------------------------------------
```

The program starts with 12 students from a seed array and the array is resized while the program runs when records are added or removed.

### 1. Data structures

Two structures do all the work:

```c
typedef struct {
  int id;
  char name[48];
  char course[40];
  int grade;
} Student;

typedef struct {
  Student *items;
  int count;
  int capacity;
} StudentList;
```

`count` is how many records are in use and `capacity` is how many slots were
allocated. Keeping the two separate is what allows the array to grow and shrink.

### 2. Dynamic memory

- The array starts as `calloc(10, sizeof(Student))`, so unused slots are zeroed.
- When a record is added and the array is full, `ensure_capacity()` doubles the capacity with `realloc`.
- When records are removed and the array is only a quarter full, `shrink_if_parse()` halves it, but never below the starting size.
- Every `realloc` is stored in a temporary pointer first. If it returns `NULL` the old array is still valid, the operation is cancelled with a message, and no memory is lost.
- `main()` frees the array once at the end.

The `[mem]` lines printed by the program make this visible. From
`docs/evidence/add_remove_proof.txt`:

```
  [mem] capacity 0 -> 10 (initial calloc)
  [mem] capacity 10 -> 20 (grew)
  [mem] capacity 20 -> 40 (grew)      <- the 21st record was added
  [mem] capacity 40 -> 20 (shrunk)    <- back down to 10 records
```

### 3. Function pointers

Function pointers are used twice, for two different jobs.

**a) The menu dispatch.** Every operation has the same signature
`void f(StudentList *)`, so the menu can call through a table instead of a
`switch`:

```c
typedef void (*Operation)(StudentList *);

Operation operations[] = {add_student, display_students, sort_students, ...};
...
operations[choice - 1](&list);
```

Adding an operation means adding one function and one label, not editing a
`switch` statement.

**b) Sorting.** `qsort()` takes a comparator function pointer, and the program
has three of them. The user's sort choice decides which pointer is passed:

```c
int (*comparator)(const void *, const void *);
...
qsort(list->items, list->count, sizeof(Student), comparator);
```

### 4. Pointer traversal and string comparison

Displaying, the average, the top student, the below-pass count and searching all
walk the array with pointers instead of an index:

```c
const Student *p;
for (p = list->items; p < list->items + list->count; p++) {
  ...
}
```

Names are compared with `strcmp()` inside `str_compare_insensitive()`, which
lowercases both strings first so searching and sorting ignore case.

All input is read with `fgets()`. If a line is longer than the buffer the rest of
the line is thrown away and the input is rejected, so a long line can never
overflow the array or push the next prompt out of step.

### 5. Custom analysis - Academic Risk Index (ARI)

The idea: two students on 45 are not in the same situation if one class averages
48 and the other averages 80. So the index looks at how far a student is below
the pass mark **and** how far they are below the class average.

```
deficit      = max(0, PASS_MARK - grade)
relative_gap = max(0, class_average - grade)
ARI          = 100 * (0.6 * deficit / PASS_MARK + 0.4 * relative_gap / 100)
```

Both parts are fractions between 0 and 1, so the index stays between 0 and 100.

| ARI | Band | Meaning |
|---|---|---|
| below 10 | Secure | passing, and not far below the class |
| 10 to 25 | Low | small gap, recoverable |
| 25 to 50 | Moderate | clearly behind |
| 50 and above | High | failing and far below the class |

From a run with a class average of 63.33:

| ID | Grade | Deficit | Relative gap | ARI | Band |
|---|---|---|---|---|---|
| 1004 | 52 | 0.0 | 11.3 | 4.5 | Secure |
| 1005 | 47 | 3.0 | 16.3 | 10.1 | Low |
| 1006 | 39 | 11.0 | 24.3 | 22.9 | Low |
| 1010 | 33 | 17.0 | 30.3 | 32.5 | Moderate |

The absolute part is weighted 0.6 because that is the part that actually fails a
student; the relative part (0.4) shows a student slipping behind a strong class.
The ARI measures the size of a gap, not pass or fail, so the program also reports
how many students are below the pass mark.

### 6. Validation

| Input | Rule | What happens if it is wrong |
|---|---|---|
| menu choice | 1 to 10 | message, menu shown again |
| student ID | whole number, above 0, not already used | duplicate IDs are rejected and the owner's name is printed |
| name | not empty, letters / spaces / hyphen / apostrophe | rejected with the reason |
| course | not empty, fits in the field | rejected with the reason |
| grade | whole number 0 to 100 | letters, negatives and 101+ are rejected |
| unknown ID on remove or search | must exist | "no student with ID" message |

`docs/evidence/validation_session.txt` shows a duplicate ID, a grade of `abc`, a
grade of 101, a name with digits and an unknown ID all rejected, with the record
count unchanged each time.

### 7. How it was tested

- Builds with `gcc -Wall -Wextra -std=c11 -pedantic` and no warnings (`docs/evidence/compile.log`).
- Every menu option was run in one session: `outputs/sample_run.txt`.
- Growth and shrink were captured in `docs/evidence/add_remove_proof.txt`.
- A separate Python script re-calculated the average, the top student, every ARI,
  the bands and the summary figures from the recorded output and compared them
  with what the program printed: 24 checks, all passed
  (`docs/evidence/verification_report.txt`).
- The program was rebuilt with `-fsanitize=address,undefined` and run again with
  no errors and no leaks (`docs/evidence/sanitizer_run.txt`).
