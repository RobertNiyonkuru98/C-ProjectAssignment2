# P3 - Dynamic IoT Event Monitoring and Callback Engine

## What the program does

The program keeps a list of IoT devices, generates readings for them, and sends
each reading to a callback function that decides whether the device is working
normally:

```
------------------------- MENU -------------------------
 1. Register a new device
 2. Display all registered devices
 3. Remove a device by ID
 4. Generate simulated readings
 5. Display detected alerts
 6. Monitoring summary
 7. Exit
--------------------------------------------------------
```

It starts with four devices covering the three required types, and option 4
generates twelve readings in one run.

### 1. The device structure and the union

```c
typedef struct {
  int id;
  char name[NAME_MAX];
  int type;
  union {
    float temperature;   // used when type is 1
    int pressure;        // used when type is 2
    float voltage;       // used when type is 3
  } reading;
  int status;
  float last_value;      // previous reading, used by the drift detector
  int has_last;
} Device;
```

The three members of the union share the same memory, so only one of them is
meaningful at a time. The program always uses `type` to decide which member to
write and which to read. For example, in `display_devices()`:

```c
if (p->type == TYPE_TEMPERATURE) {
  sprintf(reading, "%.1f C", p->reading.temperature);
} else if (p->type == TYPE_PRESSURE) {
  sprintf(reading, "%d kPa", p->reading.pressure);
} else {
  sprintf(reading, "%.2f V", p->reading.voltage);
}
```

### 2. Callback dispatch

The brief asks for this interface:

```c
void process_device(Device *device, void (*callback)(Device *));
```

It calls whichever function it is given. The device type decides which function
that is, through `callback_for_type()`:

```c
process_device(d, callback_for_type(d->type));   // the type's own callback
process_device(d, drift_monitor);                // the custom callback
```

Adding a new device type means adding one callback and one line in
`callback_for_type()`, not editing a large if/else chain in the monitoring code.

### 3. The three required callbacks and their limits

| Device type | Callback | Operating limits | Alert when |
|---|---|---|---|
| Temperature sensor | `temperature_monitor` | 18 to 35 degrees C | below 18 or above 35 |
| Pressure sensor | `pressure_monitor` | 98 to 108 kPa | below 98 or above 108 |
| Battery monitor | `battery_monitor` | 3.30 to 4.20 V | below 3.30 or above 4.20 |

Each callback sets the device status, prints a one line result, and records the
full alert through `add_alert()`.

### 4. The custom callback - Sensor Drift Detector

A reading that jumps much more than it should between two readings is more
likely to be a failing sensor than a real change in the process. `drift_monitor()`
stores the previous reading on the device and compares:

```
change = |current reading - previous reading|

temperature : drift if change > 5.00 C
pressure    : drift if change > 3 kPa
battery     : drift if change > 0.30 V
```

When the change is too large it prints the size of the jump, counts it in the
monitor, and stores an alert with the expected value "change between readings".
The threshold is different for each type because a 5 degree change in a boiler
is normal while a 5 kPa change in a gas line is not.

### 5. Simulated readings

- `srand(time(NULL))` seeds the generator with the current time, so each run is different.
- Temperature readings are drawn between 15 and 45 degrees C.
- Pressure readings are drawn between 95 and 110 kPa.
- Battery readings are drawn between 3.00 and 4.20 V.
- Every fourth reading is deliberately pushed outside the operating limits, so the
  alert path is exercised as well as the normal path.
- Twelve readings are generated in a run, round robin across the registered devices,
  which means one device can generate several readings in the same run.

### 6. Alerts

Every alert stores and prints the device ID and name, the reading and its unit,
the expected range, the reason, and the callback that raised it - which is what
the brief asks for. Alerts are held in their own dynamically allocated array that
starts at 8 entries and doubles when full.

From `outputs/sample_run.txt`, after registering a fifth device:

```
    Temperature sensor   : 9

```

Example alert lines from the same run:

```
  ALERT  Boiler Room Temp       17.5 C  below 18.0 C
  ALERT  Main Line Pressure       95 kPa below 98 kPa
  ALERT  Backup Battery         3.01 V  below 3.30 V
  DRIFT  Boiler Room Temp     moved 21.89 C since the last reading (limit 5.00)
```

Removing the fifth device afterwards took the device count back from 5 to 4 and
kept every other record intact.

### 8. Memory

- The device array starts at 4 slots and doubles when it is full.
- It is halved when it becomes a quarter full, never below the starting size.
- The alert array starts at 8 slots and doubles when it is full.
- Every allocation is checked before it is used.
- `main()` frees both arrays once at the end.
